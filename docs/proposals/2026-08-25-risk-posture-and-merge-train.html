agentic-kanban · design proposal · 2026-08-25

Risk posture per project, and a merge train that actually runs

The board was built for one careful ticket at a time on an idle machine. It now runs 100-ticket backlogs on a box that swaps. This document says where the time goes (measured), why, and what to build — ordered so the first day of work removes the biggest stalls.

Sources: five parallel code/data investigations of the repo, the live DB, git history, conductor logs, and hook-cost.mjs over the last 7 days. Every number below has a file or query behind it.

Three more facts frame everything else:

  • The gate is a resource failure, not a code failure. #846 ran the gate 15 times (21–44 min each, ~10 h) and merged nothing; the 3 failing suites pass in 22 s on an idle box. "The retry is the load." While any gate holds the build semaphore, every monitor-mode project is held from starting work (verify_gate_running, monitor-auto-start.ts:671).
  • 77% of merged workspaces needed more than one session, and stopped/hung builder sessions average 173 min of wall-clock each — that, not the agent's work, dominates cycle time.
  • The team already does the merge train by hand. CONTINUE.md records a direct-master batch that drained 26 tickets with one gate per batch, and notes the batched gate found defects no individual ticket's suites could see. The board cannot do this for itself.

2. Five root causes

2.1 The merge train exists but is unreachable

merge-train.service.ts assembles N branches onto kanban/train/<label>, gates the assembled tree once, bisects on red, lands with --no-ff. But executeQueue only chooses it when recommendedStrategy === "integration-union" — i.e. when branches overlap in files. Independent branches, the textbook train input, go down the sequential path and pay one gate each. strategy is not even in the POST /api/merge-queue wire schema, and the only production caller (auto-merge-orchestrator.ts:368) never asks for it.

2.2 Nothing reads the machine

Five independent throttles — WIP, maxNewStartsPerCycle, build semaphore (fixed 2), verify_max_workers (pref, 1..32), git spawn slots (8) — and not one consults RAM, CPU or swap. agent.service.ts:542 spawns a ~520 MB claude.exe unconditionally. The one machine-aware check in the repo is a Claude hook (machine-capacity.js), outside the server. Meanwhile fleet gate --json already answers "can this box start another process?" and four separate sessions in CONTINUE.md deferred work because of it — by hand.

2.3 The hook chain has two bugs and one design flaw

  • Bug: scoped-vitest.js:150 references overBudget/budget/budgetMessage that are never imported → ReferenceError on the success path → every green test run becomes decision:"block". The agent is told to fix a passing suite.
  • Bug: remind-cleanup.js is alwaysRun with no stop_hook_active escape → an agent that started pnpm dev (as the dev-server skill suggests) cannot finish until it kills its own server.
  • Design: the generated Typecheck rule has no events, so it defaults to PostToolUse and Stop — a whole-monorepo tsc per edit, measured at median 5m37s × 207 calls = 47.9% of all hook time. Locally mitigated by emptying a gitignored file that three server call sites regenerate (#868), and that no worktree inherits.

2.4 Selection is FIFO by issue number

runTodoPull orders by issue_number. issues.priority is never read on the start path. Strategy Bullseye weights only choose refill focus and provider — they do not reorder anything. Hard caps of 2 relaunches and 2 merges per cycle board-wide are constants.

2.5 The only verdict is binary

There is no risk mode, no fast lane, no red-test budget. verify_gate_strategy weakens scope, never the verdict. scoped-base-watch — the tier that was supposed to let base-branch health be the backstop — is inert: resolveGateScoping never branches on it, although base-branch-health.service.ts is built and probing. So the default stays full.

3. Risk posture: one dial, four settings

Today an operator who wants speed must align eight prefs by hand (verify_gate_strategy, auto_review, review_auto_fix, quiesce_builders_during_gate, file_contention, verify_max_workers, Bullseye WIP, merge strategy). The proposal is a single per-project pref, risk_posture_<projectId>, resolved by one function that fans out to every consumer — exactly the pattern resolveStartPolicy established in decision 008, and the same argument: one dial is a kill-switch and an explanation; eight prefs are a drift.

The rule that makes this honest: a weaker posture may only weaken verification visibly — the same rule the gate tiers already follow. Every merge message names the posture and what was skipped; the board view shows a posture chip per project; red-debt is a first-class count on the board, not a silent state. Posture is per project by default, overridable per ticket (a risk:strict tag pins a migration ticket to the strict lane inside a sprint project), and the Conductor's objective.md block should render it so the LLM monitor and the deterministic engine agree.

4. The merge train as the landing path

Make the train the default for the auto-merge orchestrator, not an accident of file overlap. The engine needs four additions rather than a rewrite:

  1. Reachability. In executeQueue: wantsTrain = trainEligible && (strategy==="train" || posture.trainMaxSize > 1). Add strategy to the wire schema and the MergeQueuePanel so an operator can force either path.
  2. Batching window. Today the 30 s tick lands whatever is ready. A train should wait: collect ready workspaces until trainMaxSize is reached, trainMaxWaitMs elapses, or the box goes idle (see §5). This is where the whole win comes from — one 30-minute gate for eight tickets instead of eight.
  3. Stacking, not just assembling. Members are rebased onto the train tip in least-overlap order (the queue already computes this) so the gate sees exactly the tree that lands. A member that conflicts with the train tip is dropped to the next train, not blocking this one — skipOnConflict semantics preserved.
  4. Persistence and a view. A merge_trains row (label, members, state, gate evidence, bisect result) so a train survives a tsx watch restart — #893's "a merge is a POST held open for 40 minutes" problem, solved for trains at the same time. A "Merge train" panel: what is aboard, what is waiting, last gate, red-debt delta.

Review on the train. In fast posture the reviewer session is launched once per train with the assembled diff and the member ticket list. One review agent reading a 300-line combined diff is cheaper and better than four reading 75 lines each without context of their neighbours — which is what the hand-batched runs in CONTINUE.md already observed. The code-review skill needs a {{members}} placeholder; nothing else changes.

Bisect stays. landGreenest already lands the green prefix and attributes red to a member. In sprint posture the attribution becomes a comment on the member's ticket plus a red-debt entry, instead of a rejection.

5. Machine-aware admission

Every start decision — new builder, gate, train assembly, hook test run — should pass one predicate: can this box afford it right now? Build it in two tiers so the cheap check runs first:

  • Tier 0 (zero spawn): port capacityHold() from machine-capacity.js into packages/shared/src/lib/machine-capacity.ts: os.freemem() with the documented 2 GB / skew calibration. Used by hooks (per turn) and as a pre-check.
  • Tier 1 (one spawn per monitor cycle): fleet snapshot --json → verdict.canStartAnother, system.headroomProcesses (the right field for a whole claude.exe), system.memory.thrashing. Cached for the cycle. Absent tool → fall back to Tier 0, and say so in the monitor status.

Then wire it where the constants are:

The multiplier the semaphore cannot see: the checkout currently holds five agent worktrees, each able to run its own pnpm test:mine — one vitest parent plus cpus/2 = 8 forks apiece, uncapped, because KANBAN_TEST_MAX_WORKERS is set only by the gate. The board's accounting says "at most 2 gates × 2 workers" while the box may carry five agent-driven vitest fleets on top. That is the concrete shape of "the retry is the load".

Naming note: the monitor already renders "the fleet gate held this project" for the worker fleet (fleetHold, #774/#801). The new skip reason must not contain "fleet" — machine_saturated keeps it distinguishable in the same warning string.

One more lever the numbers justify: builder test runs are the dominant invisible load. In fast/sprint posture the builder's Stop hook does not run vitest at all — the train's gate runs it once for everyone. That alone removes the "3 vitest suites in parallel block the whole system" case, because only the board's own semaphore can spawn vitest.

6. Hooks: fix the bugs, then make them adaptive

Day one (an hour of work, removes most of the stall)

  1. scoped-vitest.js: import the budget helpers, declare budget/overBudget, pass timeout to spawnSync, call killTree (killed vitest fleets currently survive reparented).
  2. remind-cleanup.js: drop alwaysRun or add the stop_hook_active bail that check-uncommitted.js:1126 already has.
  3. smart-hooks-rules.ts:84: events: ["Stop"] on the Typecheck rule — fixes #868 at the generator, reaches worktrees and every other project.
  4. settings.json: collapse the three Bash|PowerShell PreToolUse entries into one runner call (3 node cold starts → 1 per shell call); explicit timeout on every entry (Codex's 10 s is the precedent; one untimed guard burned 9h34m).
  5. check-skill-frontmatter.js: exit 2 or delete — 1 h/week for a block that is probably not honoured.

Then: hooks that read posture and capacity

The runner already has a config layer (smart-hooks-config.json) and the board already writes ticket context into every worktree. Add two inputs to the runner:

  • Posture, from the ticket-context file: strict runs typecheck + related tests on Stop; standard the same but capacity-gated (today's intent); fast typecheck only; sprint only the safety guards (DB, cross-worktree). Safety guards never change with posture.
  • Capacity, Tier 0, before any spawn — including the generated rules, which today bypass capacityHold entirely. A held check is reported as inconclusive, not as a block, and the board's train gate is named as the thing that will run it.

Also worth doing: check-uncommitted.js re-reads the whole session transcript plus up to 200 subagent transcripts under a 10 s budget, twice per failing check. Cache the last-parsed offset per session; the check silently stops working on exactly the long sessions where it matters.

7. Scheduling 100 tickets

  • Score, don't FIFO. Replace ORDER BY issue_number with a score: priority × unblock_count × age / predicted_cost. buildDependencyWavePlan already computes unblock counts; budget-estimator.service.ts already estimates cost; neither feeds the start path. Bullseye weights become a term in the score, which is what the UI already implies they are.
  • Seed coupled_with from touchedFilesJson. Group formation needs edges; a cold backlog has none. The contention predictor already knows which tickets touch the same files — the same data is a grouping proposal. Run it as part of decompose/import, preview-first, so auto_group_coupled has something to work with on day one.
  • Lift the constants into posture. MAX_MONITOR_MERGES_PER_CYCLE = 2 and relaunches = 2 are board-wide ceilings of ~30 merges/hour; with a train they are per-train anyway. Raise activeAgentsTarget's clamp of 12 once WIP is machine-derived (§5) — the clamp was a safety net for exactly the case that admission control now covers.
  • Fix the refill floor. runBacklogEmptyStrategy counts eligible tickets without allowFeatureTypes; a 100-feature backlog reads as "floor not met" and the refiller keeps generating beside it.
  • Reconcile WIP. wip_limit_<id> (dependency waves), Bullseye activeAgentsTarget (monitor), and drive-preflight's bypass are three surfaces for one number. One resolver.
  • Per-ticket "why not running". Skip reasons are per-project tallies; with 100 tickets you get {wip_cap: 87}. Persist the last skip reason on the issue so the board can show it.

8. "Eventually green"

The requirement is that all tests pass eventually, not after every ticket. That needs three things the board does not have:

  1. A red-debt ledger. base_branch_health already stores which suites are red on master after each merge. Promote it: a red_debt set per project (suite, since-commit, attributed ticket, owner ticket). A train in fast posture may land when its red set is a subset of the ledger; new red is attributed by bisect and either rejected (fast) or added to the ledger with a debt ticket (sprint).
  2. Make scoped-base-watch real. Connect resolveGateScoping to base-health: scoped gate per train, full suite as a scheduled base probe (idle hours, or "after every N trains"). The probe's failures go to the ledger, not to whichever ticket happened to be gating.
  3. A debt cap that flips posture. sprint with a ledger over N entries or older than T degrades to fast automatically, and the board says so — the same shape as the profile-allowlist hold: refuse to keep going quietly. Paying down debt is a ticket the refiller files, prioritised by the score in §7.

Flake handling changes shape with this: a flaky suite is quarantined into the ledger with a flaky tag rather than costing a 45-minute re-run (#894 already re-runs only the failed suites; the ledger makes the quarantine durable).

10. Risks and open questions

  • Train attribution on red. Bisect is O(k log n) gates for k bad members — on a bad day a train of 8 with 3 red members costs more than 8 sequential gates. Mitigation: cap bisect depth by posture; in sprint attribute by the cheap targeted re-run (#894) instead of bisect.
  • Review quality on a combined diff. One reviewer over 8 tickets may miss per-ticket acceptance criteria. Mitigation: the train review prompt lists each member's criteria; strict/standard keep per-ticket review. Measure with review-effectiveness.service.ts before making train review the fast default.
  • Direct-master bypass. ~90% of tickets already skip the gate path. A train that is fast enough should pull that work back onto the board; if it does not, the posture dial is tuning the minority path. Track the ratio.
  • fleet is a sibling tool, not a dependency. Tier 1 must degrade to Tier 0 cleanly on machines without claude-pick — and the snapshot's Windows-specific fields (kernel pool, standby) will be absent elsewhere.
  • The conductor and the engine. The hand-written FOCUS POLICY block outranks generated tunables and is invisible to the in-process engine. Posture should be rendered into objective.md like the tunables are, so there is one answer to "how careful are we on this project".
  • Not measured: why builder sessions stop at 173 min mean, per-stage review→merge latency, hook tax for the invisible PreToolUse guards. Step 1's gate-duration persistence and a per-session stage timestamp are the cheapest way to get these.
