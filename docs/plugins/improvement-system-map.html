How the parts improve existing software — and how they feed each other

One board is the host. Three plugins split the work into protect, find potential and change safely; every plugin's findings become tickets the board can drive, and the board's own metrics view keeps the trend. Read the loop first, then each part's role, then how a single finding travels.

The loop

Five stages, each owned by one part; the arrows are real data hand-offs (tickets, JSON, metrics rows), not aspiration. The last stage feeds the first — friction from refactoring hardens the toolset, and re-measurement re-plans the work.

1 · UNDERSTAND & PROTECT

What does it do, and is that pinned?

Bounded contexts → per-module requirements register → tests bound to requirements → functional-coverage dashboard, observed UI graph, page-object SDK.

safety-net
2 · MEASURE

Where is the debt, structurally?

Hotspots, coupling, god objects, module clustering, dependency graph — and the shared import graph the safety net's module cut now runs on.

code-metrics
3 · FIND POTENTIAL

What should change, and why?

Module decomposition plan · the pattern language the code uses (elements, rules, rings) · refactoring scout (workarounds a minimal abstraction replaces) · one architecture index to move.

code-metrics
4 · CHANGE SAFELY

Do it without breaking consumers

Deterministic verbs — rename, move-method, extract-service, change-sig, safe-delete, impact, check — across TS/Ruby/PHP/Python/JVM/Go, applied by builders in worktrees, gated by review and the safety net's tests.

refactorboard
5 · TRACK & LEARN

Did it help — and what did the tools lack?

Re-measure (arch-index, patterns --diff, scorecard) → Quality Metrics trend per commit; verb gaps → refactor-tool: tickets → lab rounds.

Rule of thumb: measure before you plan, protect before you change, re-measure after. Skipping stage 1 on a codebase you don't know is how a "safe" rename becomes a production incident; skipping stage 5 is how nobody can tell whether the effort paid.

How one finding travels

Take the pattern-language finding the tool surfaced today, to show the loop end to end.

measure
arch-plan reports 6 violating edges

5 × server-service→server-monitor, 1 × shared-schema→shared-lib — the second is new since the round-1 baseline (a #523 re-export).

ticket
#618 filed against agentic-kanban

Verdict candidates spelled out (real / rule wrong / boundary wrong), the ledger to update, the re-measure command.

change
Builder fixes it with the verbs

e.g. move-symbol / import repoint in a worktree; if a verb refuses the shape → refactor-friction files a refactor-tool: ticket and the builder carries on.

gate
Review + safety-net tests + pre-merge gate

Behaviour pinned by the register's tests is what makes the structural change safe to merge.

track
Re-measure → Quality Metrics

patterns.violations 6 → 5, arch.pattern_consistency up; the loop's next advance re-plans from what is left; the friction ticket waits for a lab round.
